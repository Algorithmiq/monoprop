---
title: Truncation and cutoffs
description: Controlling operator growth with structural cutoffs and coefficient-tolerance thresholds.
---

monoprop limits the growth of the propagated operator with two independent
mechanisms: a **structural cutoff** on the size of each monomial, and
**coefficient-tolerance** thresholds on the magnitude of each term. Both can be
changed at any point during a simulation. Graph builds can also bound the number
of sine branches on the paths to each monomial
([max-sins truncation](#max-sins-truncation)).

The structural cutoff discards monomials that grow "too large". What counts as
large depends on the simulator: [MajoranaPropagator][] offers a choice between two
measures of a Majorana monomial, while [PauliPropagator][] always measures a term
by its qubit **Pauli weight**.

## The fully-paired rule

Whatever the measure, the structural cutoff shares one exception: a monomial
that is **fully paired** — every Majorana operator it contains comes as a
complete pair $m_{2j-1}m_{2j}$ on some mode, or, in qubit space, the monomial is
a product of Pauli-$Z$ operators — is *always kept*, regardless of
its size. Fully paired monomials are exactly the terms that can contribute to an
expectation value against a product reference state, so discarding them would
throw away signal (see [Propagation Algorithm](/concepts/algorithm)). The cutoff
therefore only ever prunes the remaining, partially paired monomials.

## Majorana operators: `length` or `support`

[MajoranaPropagator][] measures each monomial as a Majorana operator and offers
two structural cutoff strategies, selected with `cutoff_type`:

**`length` (default).**
Keeps a monomial when its **length** — the number of Majorana operators $m_j$ it
contains — does not exceed the cutoff. Short monomials dominate typical
expectation values, so bounding the length retains the dominant contributions;
this is the physically motivated choice for quantum chemistry Hamiltonians. For
example, $M_\nu = m_1 m_2 m_5$ has length 3, so a `length` cutoff of 2 discards
it.

**`support`.**
Keeps a monomial when the number of distinct **modes** it touches (its support)
does not exceed the cutoff. Because one mode can carry two operators, this is
coarser than length, useful when the ordering encodes spatial locality. The same
$M_\nu = m_1 m_2 m_5$ touches only mode 1 (both $m_1$ and $m_2$) and mode 3
($m_5$), so its support is 2 and a `support` cutoff of 2 keeps it.

## Qubit operators: Pauli weight

[PauliPropagator][] accepts Pauli operators and gates directly and measures each
term by its **Pauli weight** — the number of qubits it touches. This is the only
structural measure: `cutoff` bounds the Pauli weight.

## Blockwise truncation

By default the structural cutoff is applied after every **rotation**, and a gate
whose generator has several commuting terms is applied as one rotation per term.
A fermionic single or double excitation, for example, expands into 2 or 8
commuting Majorana strings, so the result depends on the order of the strings
inside one physical gate.

`truncation_blocks` on
[build_graph][monoprop.monomial_propagator.MonomialPropagator.build_graph] groups
consecutive gates into **blocks**. Inside a block no structural cutoff applies, so
every branch is kept. At the end of the block, every monomial the block created
that is unpaired and over the cutoff is dropped. A monomial may therefore pass
through a long intermediate inside a block; the short monomials it branched into
survive.

- `truncation_blocks="gate"` makes every gate its own block, so each gate is
  truncated once, independently of the order of its commuting terms. This is the
  common case.
- A sequence gives one block label per entry of `circuit.gates`, for blocks that
  span several gates (for example one c-tUPS tile). Each label must form one
  contiguous run of gates.
- `None` (the default) is standard truncation. A circuit of single-term gates
  built with `"gate"` gives exactly the same result.

```python notest
sim.build_graph(circuit, truncation_blocks="gate")
sim.build_graph(circuit, truncation_blocks=["tile0", "tile0", "tile0", "tile1", "tile1", "tile1"])
```

The Heisenberg sweep consumes gates from last to first, so a block's truncation
point comes after its *first* gate in circuit order. The Schrödinger picture applies
gates from first to last, so there it comes after the block's *last* gate. Blocks
keep more monomials than per-rotation truncation at the same cutoff, so expect a
larger graph. A dropped monomial also stays in memory: `size()` counts it, but
nothing reads it again, and a later gate that produces the same monomial starts it
afresh.

Blockwise truncation works with every coefficient tolerance, partitioning and MPI.
`lower_atol` still applies to every rotation. With `upper_atol`, a seeded build
also keeps an unpaired monomial over the cutoff at a block end when its coefficient
there is at least `upper_atol`. An unseeded build has no coefficients, so
`upper_atol` plays no part, just as in standard truncation.

Restrictions and differences:

- [propagate][monoprop.monomial_propagator.MonomialPropagator.propagate] takes no
  blocks.
- A block cannot span two `build_graph` calls: every call closes its last block.
- The initial operator (the observable, or in the Schrödinger picture the state) is
  never truncated, so only monomials created inside a block are dropped.
- A block's last rotation keeps the cutoff of standard truncation, so a partner it
  would create only to drop is never stored. There, two terms that are both unpaired
  and over the cutoff exchange weight only if one of their sine terms reaches
  `upper_atol`. Without `upper_atol`, this only affects the unpaired terms of a
  Heisenberg observable that are over the cutoff. With it, it also affects terms
  that a block end keeps. When every unpaired term of the observable is within the
  cutoff (molecular Hamiltonians at a length cutoff of 4 or more), or in the
  Schrödinger picture, and `upper_atol` is unset, blockwise truncation is exactly
  the rule above.
- In the Schrödinger picture, the state starts with the paired monomials that
  `schrodinger_cutoff` admits, and any other paired monomial enters when a rotation
  first reaches it. When that cutoff leaves out paired monomials a gate reaches, the
  result can depend on the order of the gate's terms even with `"gate"` blocks.

## Max-sins truncation

Every rotation splits a monomial that anticommutes with the generator into a
cosine branch, the monomial itself, and a sine branch, its partner (see
[Propagation Algorithm](/concepts/algorithm)). For small angles, a monomial
reached only along paths with many sine branches carries a small coefficient.
**Max-sins truncation** bounds that count, independently of the angles, so it
suits a graph that is built once and evaluated at many parameter values:

```python notest
sim = MajoranaPropagator(hamiltonian, initial_state, cutoff=6, max_sins=4)
sim.build_graph(circuit)
```

The rule follows [PauliPropagation.jl](https://github.com/MSRudolph/PauliPropagation.jl)'s
`max_sins`:

- Every monomial carries the fewest sine branches on any path that reached it.
  The initial operator (the observable, or in the Schrödinger picture the state)
  starts at 0.
- A rotation gives the partner its source's count plus one. When the partner
  already exists, the rotation is always kept, and both monomials keep the smaller
  of their own count and their partner's plus one.
- A partner that does not exist yet is created only if its count is at most
  `max_sins`. Otherwise the source is only cosine-scaled. This is the only thing
  max-sins truncation drops.

`max_sins=0` therefore only rotates monomials into each other that already exist,
and a larger `max_sins` never keeps fewer monomials. It is applied at every
rotation, together with the structural cutoff, `lower_atol` and blockwise
truncation: a partner must pass every active rule. It works with partitioning, MPI
and both bases, at one byte of memory per monomial (`sin_count_bytes` in
`operator_memory_breakdown()`).

The counts carry over between `build_graph` calls, so an extension continues them.
Two controls change that:

- `build_graph(circuit, count_sins=False)` makes the call's sine branches free: a
  partner takes its source's count, so the call creates every monomial it would
  without max-sins truncation, while the counts stay up to date for later calls.
  Use it for gates that should not spend the budget, such as candidate orbital
  rotations appended to a built graph.
- `reset_sin_counts()` sets every count to 0, so later calls spend the whole
  budget again from the current operator. Setting `max_sins` from `None` to a
  value does the same.

```python notest
sim.build_graph(ansatz)                          # counted
sim.build_graph(candidates, count_sins=False)    # free
sim.max_sins = None                              # off: frees the counts
```

Restrictions and differences:

- Max-sins truncation applies to `build_graph` only;
  [propagate][monoprop.monomial_propagator.MonomialPropagator.propagate] raises a
  `ValueError` while `max_sins` is set.
- Lowering `max_sins` does not drop monomials that already exist; it only stops
  new ones.
- In the Schrödinger picture every fully paired monomial is part of the reference
  state, even before a rotation first reaches it, so it counts 0 and is never
  declined.
- `max_sins` is at most 254, since each count is stored in one byte.

## Gate-application length cap

[MonomialPropagator.build_graph][monomial_propagator.MonomialPropagator.build_graph]
and [MonomialPropagator.propagate][monomial_propagator.MonomialPropagator.propagate] accept
`only_rotate_len_k` to apply gates only to terms whose length is at most `k`.
This is independent of the structural cutoff. Omitting the argument or passing
`None` imposes no additional gate-application cap.

## Coefficient tolerance filtering

Two absolute-tolerance thresholds prune terms by coefficient magnitude,
independently of the structural cutoff:

- `lower_atol`: discard terms with `|coeff| < lower_atol` during gate
  application. Primary tool for suppressing negligible branches in long
  ADAPT loops.
- `upper_atol`: accept terms with `|coeff| > upper_atol` regardless of the structural cutoff. Useful for
  keeping a few large terms that would otherwise be discarded by a tight cutoff.

```python notest
sim.lower_atol = 1e-9
sim.upper_atol = 1e-3
```
Note that choosing a very low value for `upper_atol` results in an increased number of
kept Majorana monomials, which eventually may even grow exponentially in the number of gates.
