monoprop core ships no framework-specific conversion code. Circuit/operator
conversion to and from other frameworks (e.g. PennyLane) lives in its own,
separately pip-installable distribution -- `monoprop-pennylane` is the
reference example -- and attaches itself to the `monoprop` namespace through a
generic plugin mechanism, so installing the package is enough: no manual
submodule import is required.

## The `monoprop.plugins` entry point

A plugin is any distribution that registers a `monoprop.plugins` entry point
whose value is an importable module exposing `__all__`. On import, monoprop
core copies every name in that `__all__` onto the `monoprop` namespace, the
same way `from module import *` would -- no hook classes, no registry, no
versioning. Dunder names (e.g. a plugin's own `__version__`) are the one
exception: they are never copied, so a plugin can never shadow monoprop
core's own identity metadata, even though `__version__` is a legitimate,
independently useful member of the plugin's own `__all__` (see
`monoprop_pennylane.__all__` below).

`monoprop-pennylane`'s `pyproject.toml` registers itself this way:

```toml
[project.entry-points."monoprop.plugins"]
pennylane = "monoprop_pennylane"
```

with its top-level `monoprop_pennylane/__init__.py` re-exporting the
conversion functions and listing them in `__all__`:

```python notest
from monoprop_pennylane.conversion import (
    from_pennylane_circuit,
    from_pennylane_operator,
    to_pennylane_circuit,
    to_pennylane_operator,
)

__all__ = [
    "from_pennylane_circuit",
    "from_pennylane_operator",
    "to_pennylane_circuit",
    "to_pennylane_operator",
]
```

Once `monoprop-pennylane` is installed alongside `monoprop`, its four
functions are available directly off `monoprop`:

```python notest
import monoprop

monoprop.from_pennylane_operator(...)
```

## Writing a plugin

Any distribution can attach to `monoprop` this way: depend on `monoprop`,
expose the public functionality from one importable module with an accurate
`__all__`, and register that module under the `monoprop.plugins` entry-point
group. Plugins are loaded once, at `import monoprop` time, after every name
monoprop core itself exports is already bound -- a plugin can safely
`import monoprop` at its own import time, which `monoprop_pennylane` relies
on implicitly.

Plugins load in whatever order `importlib.metadata.entry_points` returns
them. A name collision between two installed plugins (or between a plugin
and monoprop core itself) still resolves by last-write-wins -- the load and
splat design has no registry to arbitrate it -- but it is never silent: a
colliding name raises a [`UserWarning`](https://docs.python.org/3/library/exceptions.html#UserWarning)
naming the plugin and the name, and is never duplicated in `monoprop.__all__`.
Plugin authors should still keep their exported names scoped to their own
framework (e.g. `from_pennylane_operator`, not `from_operator`) so this stays
a rare, deliberate event rather than routine noise. Dunder names never
collide this way -- they are exempt from the splat entirely, not merely
last-write-wins -- so a plugin's `__all__` can freely include its own
`__version__` (as `monoprop_pennylane`'s does) without risking monoprop
core's.

A plugin that fails to load (an `ImportError` from a missing or broken
runtime dependency, or any other exception) is skipped with the same kind of
warning, rather than breaking `import monoprop` for every consumer in the
environment -- including ones who never touch that plugin, and other,
working plugins loaded alongside it.
