`monoprop` carries two kinds of benchmark: an **internal** pytest suite that guards against
regressions on every commit, and an **external** comparison against other open-source Pauli and
Majorana propagation engines.

## How memory is measured

Every figure on this page reports **peak resident set size**, read from the kernel's `VmHWM`
high-water mark. It is the number to quote, and the only one that is like-for-like against a
library written in another language.

- **It is exact, not sampled.** The kernel updates `VmHWM` on every RSS increase, so no
  transient can be missed and no background thread is needed, which also means the GIL cannot
  hide anything from it.
- **The window is reset per step.** Each measured region settles the process first
  (`gc.collect()` + `malloc_trim`, or `GC.gc()` + `malloc_trim` on the Julia side) and then
  resets `VmHWM` to that floor, so the peak reported is that step's own and not an earlier
  step's retained garbage. Without the settling the figure tracks the allocator's willingness
  to return pages more than it tracks what the code needed.
- **Every engine is measured by the same instrument**, from outside, over exactly the timed
  region.

It is a whole-process figure, so it includes the interpreter and the loaded libraries. That
constant is why the curves are worth reading for their *growth*, and why an engine can be
leaner in RSS while being far slower.

Where an engine also accounts for itself (`monoprop`'s `operator_memory_bytes()`,
`PauliPropagation.jl`'s `Base.summarysize`, cuPauliProp's device pool) that figure is recorded
alongside as `native_memory` and drawn as a faint companion line. **Those are not comparable
with each other**: they count different things in different pools. They are context for a
single engine's curve, never a cross-engine ranking.

<Callout type="warn">
GPU engines are the one case where host RSS says nothing: the operator lives on the card, so
`cuPauliProp`'s host RSS sits flat near 534 MB at every lattice size. Compare it with
`plot_scaling.py --memory-key working_set_MB`, which adds the device peak to the host figure.
</Callout>

## Internal benchmarks

A pytest suite measuring the **time** and **peak RSS** of `monoprop`'s core operations. It is
kept apart from the test suite and run with `just bench`.

### Running

Each run takes a **label** and becomes one column in `results/REPORT.md`, so serial, MPI and
threaded variants sit side by side. Extra arguments are forwarded to pytest.

```bash
uv sync --group bench                          # once

just bench serial                              # serial run, column "serial"
just bench-smoke                               # quick sanity check (tiny sizes)
just bench serial --num-modes 64 --bench-rounds 10

monoprop_NUM_THREADS=10 just bench serial-t10  # cap the partition count

uv run --group bench monoprop-bench-report benches/results  # rebuild report, no re-run
```

Two suites are available:

- **`bench_random.py`** — `build_graph`, `pare`, `energy`, `gradient` and `inplace` on a random
  problem. Configurable with `--gen-length` (4), `--obs-terms` (10000), `--num-generators`
  (100), `--num-modes` (128), `--cutoff` (6), `--seed` (0) and `--bench-rounds` (1); defaults in
  parentheses.
- **`bench_models.py`** — fixed models, marked `slow`: a 120-qubit Fermi-Hubbard 29-step Trotter
  run (`test_model[hubbard]`) and a 127-qubit kicked-Ising run over 20 layers
  (`test_model[pauli]`). Override any config field with `--<model>-<field>`, e.g.
  `--pauli-num-layers 30`; `just bench --help` lists them all.

Each run writes `results/time-<label>.json` (pytest-benchmark) and `<label>.json` (everything
else); `monoprop-bench-report` merges every label into `results/REPORT.md`.

### MPI

The suite is communicator-aware: operations are barrier-wrapped so the timed cost is the
**makespan** across ranks, and memory is the **peak of the summed live PSS**, replayed from
per-rank timelines. Summing each rank's independently-timed peak would count transients that
never coexisted; PSS rather than RSS so that a shared page is counted once rather than once per
rank.

```bash
just bench-build-mpi                           # build once (MPI on)
monoprop_NUM_THREADS=2 just bench-mpi r5t2 5 --map-by slot:PE=2 --bind-to core
```

<Callout type="warn">
**The MPI build must stay loaded.** `monoprop` builds `MPI=OFF` by default, and a non-MPI
extension ignores the communicator — every rank then holds the **full** operator, for N× the
memory. The recipes pass `--no-sync` so the MPI build survives; rebuild after editing sources.
`just bench-mpi` checks `monoprop.has_mpi` and aborts if it is missing.
</Callout>

### Continuous benchmarking

Every commit on `main` runs `bench_main.yml`, and the results are tracked by
[Bencher](https://bencher.dev/), which graphs them over time and alerts when a metric drifts
outside its threshold. The workflow runs the same recipes you can run locally:

```bash
just bench-ci ci-linux          # default sizes, more rounds, no slow models
just bench-bmf ci-linux         # the same results as Bencher Metric Format JSON
```

`monoprop-bench-bmf` merges both artifacts into one report because Bencher accepts a single
adapter per upload — the stock `python_pytest` adapter would keep the timings and drop
everything else. Four measures are tracked:

| Measure | Unit | Source | Threshold |
|---|---|---|---|
| `latency` | nanoseconds | pytest-benchmark mean ± 1σ | Student's t-test, upper 0.99 |
| `peak-memory` | bytes | per-operation peak RSS (`VmHWM`) | +10% |
| `resting-memory` | bytes | settled operator + graph footprint | +10% |
| `terms` | count | terms in the evolved operator | any change |

`terms` is deterministic for a fixed seed and problem size, so it is held to an exact match: any
drift is an algorithmic change and should be a deliberate one. Timings are noisy on shared
runners, so alerts on `main` are recorded but do not fail the build.

#### Testbeds

Bencher keys every metric on (branch, testbed, measure), so a testbed is one machine shape and
its history is only meaningful against itself. Changing the hardware under a testbed name shows
up as a step change in every series, which is why each machine gets its own name.

| Workflow | Runner | Testbed | Label | Profile |
|---|---|---|---|---|
| `bench_main.yml` | GitHub-hosted `ubuntu-26.04` | `ubuntu-26.04` | `ci-linux` | `not slow`, 5 rounds |
| `bench_bare_metal.yml` | [RunsOn](https://runs-on.com/) EC2 node | `aws-c7i-4xlarge` | `ci-bare-metal` | everything, 3 rounds |

The bare-metal workflow provisions a dedicated node per run, so nothing else is scheduled on it
while the benchmarks run. That lower noise floor is the point: it is what a testbed needs before
its timing thresholds can be tightened enough to gate on, and it is why it can afford the slow
fixed models the shared runner skips.

Which benchmarks run, and how many rounds each gets, are the `bench-markers` and `bench-rounds`
inputs of the reusable `bench.yml`. Changing either for a testbed that already has history
rewrites what its series measures, so pick them before the first run:

```bash
monoprop_BENCH_MARKERS= monoprop_BENCH_ROUNDS=3 just bench-ci ci-bare-metal
```

## Comparison with other packages

Standalone scripts comparing `monoprop` against other open-source Pauli and Majorana
propagation engines live in
[`packages/bench-third-party`](https://github.com/Algorithmiq/monoprop/tree/main/packages/bench-third-party).
That directory is a standalone `uv` project with its own lockfile, deliberately outside the
repository workspace: it pins CUDA-specific wheels and a narrower Python range than `monoprop`
itself.

The comparisons are measured on [Leonardo (CINECA)](https://docs.hpc.cineca.it/hpc/leonardo.html),
one exclusive DCGP node per engine:

- **CPU** 2× Intel Xeon Platinum 8480+ (112 cores, Sapphire Rapids), ~480 GB RAM
- **GPU** 1× NVIDIA A100 64 GB, for `cuPauliProp`

Each engine runs at the thread count it is fastest at, since they do not peak at the same one.
Rather than trusting that prose, read it off the data: every record carries its own `host`,
`threads` and `library_version`, and the plotting scripts print that provenance beside the
numbers they draw.

### Pauli propagation

Trotterized time evolution of a 2D transverse-field Ising model, measuring the `ZZ` correlator on
a fixed qubit pair. Two sweeps: one grows the circuit depth at a fixed lattice, the other grows
the lattice at a fixed depth.

#### Fixed lattice, increasing depth

A 12×12 lattice (144 qubits) over 28 Trotter points, `dt = 0.05`, coefficients truncated below
`1e-6`, no weight cutoff.

![Runtime and peak RSS per Trotter step for five Pauli propagation engines](/benchmarks/pauli_results.png)

`monoprop` tracks the GPU-accelerated `cuPauliProp` closely while running on CPU, and beats every
other CPU engine in both time and memory as the operator grows. Solid lines are peak RSS; the
faint companions are each engine's own accounting, for context only.

#### Increasing lattice size

The complement: circuit depth and truncation held fixed while the lattice grows from 6×6 (36
qubits) to 18×18 (324 qubits). Each engine runs the identical model at each size in its own
subprocess.

![Total runtime versus lattice size, five Pauli propagation engines](/benchmarks/pauli_scaling_runtime.png)

At a fixed coefficient truncation the operator **saturates**: past ~100 qubits every engine
carries the same ~5.84M terms whatever the lattice. This therefore measures *cost per term kept*,
not a growing problem — which is exactly why `monoprop`'s total runtime stays nearly flat, and
why the gap widens with size.

![Peak RSS versus lattice size, five Pauli propagation engines](/benchmarks/pauli_scaling_memory.png)

The same saturation shows in memory. `monoprop` goes from 871 MB at 36 qubits to 1134 MB at 324
— a 1.3× rise across a 9× larger lattice — while `PauliPropagation.jl` climbs from 1199 MB to
4185 MB, a 3.5× rise. The ratio between them widens from 1.4× to 3.7×.

![Bar chart of monoprop's speed-up over each engine, grouped by qubit count](/benchmarks/pauli_speedup.png)

| qubits | metric | PauliPropagation.jl | QuEra ppvm | Qiskit pauli-prop | cuPauliProp (GPU) |
| -----: | :----- | -----: | -----: | -----: | -----: |
| 36 | speed-up | 16× | 107× | 165× | 4.4× |
| 36 | RSS ratio | 1.4× | 0.6× | 2.6× | – |
| 100 | speed-up | 33× | 190× | 287× | 8.5× |
| 100 | RSS ratio | 2.0× | 0.7× | 5.5× | – |
| 196 | speed-up | 55× | 184× | – | 11× |
| 196 | RSS ratio | 2.6× | 0.8× | – | – |
| 324 | speed-up | 105× | – | – | 15× |
| 324 | RSS ratio | 3.7× | – | – | – |

Speed-up is wall-clock total runtime relative to `monoprop`; RSS ratio is the other engine's peak
RSS divided by `monoprop`'s, so above 1 means `monoprop` used less. A dash means the engine did
not finish that size within the 300 s per-point budget, or — for the GPU — that host RSS does not
describe it.

Three caveats belong with these ratios:

- **`QuEra ppvm` uses less memory than `monoprop`**, consistently 0.6–0.8× the peak RSS, while
  being 107–209× slower. It is the one engine that trades the other way, and the table would be
  misleading without saying so.
- **Only two of the four CPU engines use more than one core.** `QuEra ppvm` and Qiskit's
  `pauli-prop` propagate on a single core — measured at 0.99 busy cores mid-propagation — and no
  environment variable changes it: ppvm's rayon-parallel `PauliSum` lives in its `config::dashmap`
  variant while its Python bindings expose only `indexmap`, and Qiskit's `_accelerate` extension
  has no parallel path at all. These ratios are wall-clock, not per-core.
- **`PauliPropagation.jl` runs in its fastest documented configuration**, the `VectorPauliSum`
  container driven by `Performance.propagate!`, which needs the dev branch (0.8.0+). That path
  leaves duplicate Pauli strings unmerged, so it reports ~38% more terms than the exact
  `propagate` path and its expectation value differs by ~1e-4 — its term count is a storage
  count, not an operator size.

### Majorana propagation

Trotterized time evolution of the 1D Fermi-Hubbard model at 60 spinful sites over 20 layers,
tracking runtime, expectation value, term count and memory at each layer. Both engines at 24
threads.

![Term count, expectation value, runtime and peak RSS versus layer, monoprop vs MajoranaPropagation.jl](/benchmarks/majorana_results.png)

![Runtime versus circuit depth on linear axes, monoprop vs MajoranaPropagation.jl](/benchmarks/majorana_runtime.png)

Runtime also gets its own linear-axis figure, since it is the quantity most often cited alone.
`monoprop`'s curve lies along the bottom of that axis, annotated with the top of the band so that
flat reads as small rather than as zero.

Both engines simulate the same physics: the expectation values agree to within 2.0e-6 at every
layer. `monoprop` keeps 1.38× more terms at equal truncation, and still finishes the 20 layers in
**92.5 s against 2908.5 s**, a 31× speed-up overall and 29× on the final layer alone. Peak RSS is
**10.6 GB against 15.7 GB**, 1.48× less, despite the larger retained operator.

Note that only `VectorMajoranaSum` dispatches into `MajoranaPropagation.jl`'s AcceleratedKernels
path; the dict-backed `MajoranaSum` is serial regardless of thread count.

### Reproducing

Every engine is driven from one `uv` project:

```bash
cd packages/bench-third-party
uv sync    # monoprop (editable), qiskit, ppvm, pauli-prop, cuquantum-python-cu12
```

The Julia engines are optional — the Python comparisons run without them:

```bash
curl -fsSL https://install.julialang.org | sh          # juliaup + latest stable Julia
julia -e 'using Pkg; Pkg.add(["JSON", "ProgressMeter"])'
```

Then, per benchmark:

```bash
# Pauli, fixed lattice — edit settings.json first to change the model
cd pauli_prop
uv run python run_model.py        # monoprop, ppvm, qiskit, cuPauliProp
julia run_model.jl                # optional; merges PauliPropagation.jl into results.json
uv run python plot_results.py

# Pauli, lattice ladder — 5 minutes per (size, engine)
uv run python run_scaling.py --output scaling_results.jsonl \
    --timeout 300 --threads monoprop=56 juliapp=28
uv run python plot_scaling.py scaling_results.jsonl
uv run python plot_speedup.py scaling_results.jsonl

# Majorana
cd ../majorana_prop
monoprop_NUM_THREADS=56 JULIA_NUM_THREADS=28 bash run_benchmarks.sh
```

All Pauli model parameters live in
[`settings.json`](https://github.com/Algorithmiq/monoprop/blob/main/packages/bench-third-party/pauli_prop/settings.json)
and are shared by every engine, so one edit compares them all on an identical problem instance.
The output schemas, the full field lists and the per-engine caveats are documented in
[`packages/bench-third-party/README.md`](https://github.com/Algorithmiq/monoprop/tree/main/packages/bench-third-party).

<Callout type="info">
Three things that reliably bite:

- **324 qubits needs a large enough mode tier** — build with `-Dmonoprop_MAX_NUM_MODES=352`,
  since tiers come in 32-mode blocks.
- **The two Pauli benchmarks want different Julia packages.** The lattice ladder needs
  `PauliPropagation.jl` **dev (0.8.0+)** for the `Performance` submodule; the fixed-lattice
  `run_model.jl` runs on the pinned **v0.7.3**.
- **`run_model.py` and `run_model.jl` merge into the same `results.json`.** Each preserves the
  other's entries, so they can be run in either order and re-run independently — but the Qiskit
  backend needs a `monoprop` run in the *same* invocation, since its mandatory term budget
  tracks `monoprop`'s per-step term count.
</Callout>
