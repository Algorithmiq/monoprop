monoprop has one supported from-source build workflow:

- the **Python bindings** — the nanobind extension behind `import monoprop`,
  built with scikit-build-core and driven by `uv` (or `pip`);
- the **C++ unit tests** — built within the same `uv` (or `pip`) invocation.

MPI is **off by default** in every build path; you enable it explicitly. The
mechanism differs by build:

| Build | Enable MPI with |
| --- | --- |
| Python bindings and C++ tests (scikit-build / `uv` / `pip`) | `--config-settings=cmake.define.monoprop_ENABLE_MPI=ON` (or export `SKBUILD_CMAKE_ARGS="-Dmonoprop_ENABLE_MPI=ON"`) |

The prebuilt wheels published to PyPI (`pip install monoprop`) are also built
without MPI, so a from-source build is required for multi-rank runs.

## Prerequisites

- a C++23-compliant compiler; on Linux the minimum supported versions are **GCC 14** and **Clang 18**
- CMake and Ninja
- Python 3.11 or newer and the `uv` package manager (for the bindings)
- an MPI implementation such as Open MPI (only for MPI builds)
- `hwloc` (version 2.9+) and `pkg-config` (required so CMake can locate `hwloc`)

The repository ships a [DevContainer](https://containers.dev/) with all of the
above pre-configured; opening the folder in VS Code and rebuilding the container is
the quickest route to a working environment.

## Building the Python bindings

`uv` creates a virtual environment, installs the Python dependencies, and
compiles the nanobind extension in editable mode. Re-run the sync command whenever
the dependency graph or the C++ sources change.


### Without MPI (default)

```bash
uv sync --all-extras -v
```

This produces a single-process build with no MPI dependency.

### With MPI

Pass a `config-settings` override to enable MPI:

```bash
uv sync --all-extras -v \
    --config-settings=cmake.define.monoprop_ENABLE_MPI=ON
```

The same override works with `pip` when installing from a checkout:

```bash
pip install . --config-settings=cmake.define.monoprop_ENABLE_MPI=ON
```

### Compile-time tuning options

These are `cmake.define` overrides, passed exactly like `monoprop_ENABLE_MPI` above.

| Option | Default | Effect |
| --- | --- | --- |
| `monoprop_MAX_NUM_MODES` | `250` | Highest mode count instantiated. Larger values cost build time and binary size. |
| `monoprop_WIDE_TERM_INDEX` | `OFF` | 64-bit term indices, for operators past 2^32 terms on one rank. |
| `monoprop_INVIDX_CHUNK_WORDS` | `512` | Inverted-index chunk height in 64-bit fold words (512 → 32768 rows). Must divide 1024 and stay at or below it. |

`monoprop_INVIDX_CHUNK_WORDS` trades two costs against each other. Rows past the
last sealed chunk sit in a growing tail whose buffer is reserved a whole chunk at
a time, so tail bytes grow with the chunk height, while the per-chunk directory
grows as it shrinks. The default is the measured minimum of that sum at production
per-partition sizes, and the minimum is interior rather than at the bottom end
because the fold also gets slower as chunks shrink. Measured at ~226k rows per
partition:

| Chunk words | bytes/term | fold, ms/generator |
| --- | --- | --- |
| `128` | 7.33 | 0.0188 |
| `256` | 7.11 | 0.0170 |
| `512` | 7.02 | 0.0164 |
| `1024` | 8.05 | 0.0160 |

512 is the robust pick rather than merely the best one: it wins 12.8% where the
tail dominates and loses 0.6% at 777k rows where it does not. Change it only with
a memory measurement in hand.

There is no knob for the inverted index's container choice. Every (column, chunk)
cell goes to whichever container is smallest, and that rule is what makes the index
several times smaller than a tiered bitmap layout. A `monoprop_INVIDX_BITMAP_M_STAR`
option used to let you force bitmaps past a posting count, spending memory to make
the anticommutation fold faster; it was measured and removed.

The trade looked much better in a single-threaded profile than it was. Production
runs one partition per core, and those partitions compete for L3 and memory
bandwidth — exactly the resource a bitmap spends. Measured at a production
per-partition size against the smallest-container rule:

| `M_STAR` | bytes/term | fold, one core | fold, 16 partitions |
| --- | --- | --- | --- |
| off | 6.87 | 1.00× | 1.00× |
| `850` | 7.25 | 0.97× | 0.99× |
| `700` | 9.66 | 0.95× | 0.98× |
| `600` | 11.81 | 0.92× | 0.96× |

1.7× the index buys 4% of the fold under contention, and the fold is itself a
minority of `propagate` — so no setting paid for its bytes, and the option is gone
rather than shipped defaulted-off.

### Verify the install

```bash
uv run python -c "import monoprop as mp; print(mp.__version__)"
```

### Running the bindings

A serial run is just a normal Python invocation:

```bash
uv run python your_script.py
```

For a multi-rank run, launch the same script under `mpiexec` (requires an MPI
build) and pass `comm=MPI.COMM_WORLD` to the simulator:

```bash
mpiexec -n 8 uv run python your_script.py
```

See [Parallelism and distribution](/features/parallelism) for the communicator options and the
operator-partitioning controls.

## Building the C++ unit tests

The supported C++ workflow reuses the build tree produced by `uv sync`. Do not
run `cmake --preset ...` to configure this project directly: the top-level CMake
configuration expects scikit-build-core to provide Python, nanobind, and related
cache variables. Instead, first create the tree with `uv sync`, then invoke `ctest`
directly to run the C++ unit tests.

### Release tree

```bash
uv sync --all-extras -v
ctest --test-dir build/editable/Release
```

This uses the scikit-build-core Release tree at `build/editable/Release` and
runs `bin/monoprop_unit_tests.x` there.

### Debug tree

```bash
uv sync --all-extras -v --config-settings=cmake.build-type=Debug
ctest --test-dir build/editable/Debug
```

### Standalone tree (iterating on the C++ tests)

The editable trees above cannot be reconfigured in place. Their CMake cache pins the
build-isolation interpreter that scikit-build-core created and then deleted, so
`cmake --build build/editable/<type>` fails as soon as it needs to regenerate
`build.ninja` — after editing a `CMakeLists.txt`, adding a test file, or changing a
cache variable. The `skbuild-*` presets inherit the same limitation, because they only
adopt an existing tree.

For a tree you can reconfigure and rebuild freely, configure one yourself. Three cache
variables have to be supplied by hand, because scikit-build-core normally provides them:

```bash
uv sync --all-extras -v   # once, so .venv exists

nanobind_dir=$(uv run --no-project --with nanobind \
    python -c "import nanobind; print(nanobind.cmake_dir())")

cmake -S . -B build/standalone -G Ninja \
    -DCMAKE_BUILD_TYPE=Debug \
    -DPython_EXECUTABLE="$PWD/.venv/bin/python" \
    -DSKBUILD_PROJECT_VERSION_FULL=0.0.0 \
    -Dnanobind_DIR="$nanobind_dir"

cmake --build build/standalone --target monoprop_unit_tests.x -j
ctest --test-dir build/standalone/cpp/tests -L serial
```

- `nanobind_DIR` is needed because nanobind is a build-isolation-only dependency and is
  absent from `.venv`, so it cannot simply be imported. The command above resolves it into
  an ephemeral environment and asks it for its own CMake package directory.
- `Python_EXECUTABLE` is needed because `find_package(Python ... Development.Module)`
  otherwise picks up an interpreter with no development headers and fails to configure.
- `SKBUILD_PROJECT_VERSION_FULL` is needed because the install-export step passes it to
  `write_basic_package_version_file()`, which errors on an empty version. Any value works
  for a tree you are not installing from.
- Point `ctest` at `cpp/tests`, not at the tree root: the root has no
  `CTestTestfile.cmake` and would report success having run nothing.
- A `Debug` tree keeps `assert()` live (no `-DNDEBUG`), which is the point of building one —
  the operator index states its preconditions as assertions.

### Related workflows

- Use `just test-wide` for the 64-bit `monoprop_WIDE_TERM_INDEX` configuration.
- Use `just code-coverage` for the coverage build.
- Use `ctest --test-dir build/editable/Release -L serial` or `-L mpi-2` to
  filter the discovered C++ test set.
