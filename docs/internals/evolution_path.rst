Evolution Path
==============

.. admonition:: Developer reference

   This page documents internal implementation details for contributors modifying
   performance-sensitive runtime code.

``propagate`` is the entry point for all unitary evolution. It selects
one of three internal modes depending on which optional arguments are supplied.

Evolution modes
---------------

Mode 1 — Graph only (build, no contraction)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Supply only ``majoranas``. The simulator builds the graph layers but does not touch
coefficient arrays.

.. code-block:: cpp

   std::vector<VecZ> majoranas = {{0,1}, {2,3}, {0,2,1,3}};
   sim.propagate(majoranas);

Use this when you plan to call ``contract_partially`` or expectation value functionals later,
and want to defer coefficient work until then. Memory cost is proportional to graph
size only.

If ``pare_threshold`` is later enabled in an expectation value functional, monoprop builds a masked
``MPExecutionPlan`` over this stored graph. The original graph stays immutable;
exact paring happens in the execution plan.

Mode 2 — Graph with live coefficient truncation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Supply ``majoranas``, ``parameter_mapping``, ``gen_coeffs``, ``parameters``, and
``operator_coeffs``. The graph is built layer by layer while simultaneously applying
each gate to the coefficient vector; terms that fall below the tolerance cutoff are
discarded immediately.

.. code-block:: cpp

   VecZ  param_map   = {0, 0, 1};    // parameter index for each generator
   VecD  gen_coeffs  = {1.0, 1.0};   // scaling factor for each parameter
   VecD  params      = {0.3, -0.1};  // actual θ values
   VecD  coeffs      = sim.contract_partially({}, {}, {}, /*inplace=*/false);

   sim.propagate(majoranas, param_map, gen_coeffs, params, coeffs);

This is the typical mode for ADAPT-VQE inner loops: the graph grows incrementally
while small terms are pruned.

Mode 3 — Immediate contraction (no graph stored)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Supply ``majoranas``, ``parameter_mapping``, ``gen_coeffs``, and ``parameters``, but
**no** ``operator_coeffs``. The simulator applies and contracts each gate in a single
pass and discards the layer immediately. The graph is not updated.

.. code-block:: cpp

   sim.propagate(majoranas, param_map, gen_coeffs, params);

Use when you only need the final coefficient vector and memory is constrained.
Cannot be used to evaluate functionals that replay the graph.

Parameter mapping
-----------------

``parameter_mapping[i]`` gives the index into ``parameters`` for the i-th generator.
Multiple generators can share a parameter:

.. code-block::

   majoranas         = [A, B, C, D]
   parameter_mapping = [0, 1, 0, 1]   // A and C share θ₀; B and D share θ₁
   gen_coeffs        = [0.5, 0.5]     // θ₀ is scaled by 0.5 before use

The effective rotation angle for generator ``i`` is
``gen_coeffs[parameter_mapping[i]] * parameters[parameter_mapping[i]]``.

``parameter_mapping`` stays in optimizer/user order. Before replay, monoprop rewrites
those values into the order expected by the graph traversal helpers through
``map_params(...)``.

Targeting specific monomial lengths
-----------------------------------

Set ``only_rotate_len_k=k`` (where ``k > 0``) to apply gates only to monomials
of length ``<= k`` in the evolved operator even if they anticommute. This is
useful for when you apply many free fermionic gates (ie: gates generated by
length 2 Majorana monomials) before expectation value estimation in Schrödinger
picture simulations. Set ``only_rotate_len_k=0`` (the default) to disable this filter.
Do not call ``propagate`` again after applying this type of rotation.

Heisenberg vs Schrödinger order
---------------------------------

The implementation keeps a distinction between the order in which the user
supplies generators and the order required by replay.

- In **Heisenberg** picture, ``propagate(...)`` walks the supplied
  generator list from end to beginning and appends each compiled layer.
- In **Schrödinger** picture, it walks the supplied list from beginning to end
  and inserts each compiled layer at the front.

That bookkeeping means storage stays cheap while the replay helpers can still
consume layers in the order they expect through graph views and mapped parameters.

The coefficient sign passed to ``map_params(...)`` is picture-dependent:

- ``+1`` when propagating Hamiltonians
- ``-1`` when propagating states
