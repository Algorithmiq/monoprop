Interface
=========

This page describes, at a conceptual level, how a problem is expressed as input
to monoprop: the operator formats you can start from, how they relate to the
Majorana representation used internally, and how a full circuit is bundled for
simulation. For the exact constructors and arguments, see :doc:`/python-api`.

Operator formats
----------------

A problem is defined by an operator together
with a reference state. monoprop accepts operators in three forms, each suited to
a different starting point. Whatever form you choose, it is converted into the
Majorana representation (see :doc:`/concepts/notation`) before simulation.

Fermionic operators
~~~~~~~~~~~~~~~~~~~~~

The natural starting point for quantum chemistry and lattice models. An operator
is given as a weighted sum of products of fermionic creation and annihilation
operators on numbered modes (for example :math:`c_0^\dagger c_1`). monoprop maps
these into the Majorana basis through the Jordan-Wigner transformation.


.. testcode::

   from monoprop import MajoranaPropagator
   from monoprop.fermi_data import FermiOperator, FermiEvGate, FermiCircuit

   # Observable: the hopping term c_0^† c_1 + c_1^† c_0 on 4 modes
   # ('+' = creation, '-' = annihilation).
   observable = FermiOperator(
       [[(0, "+"), (1, "-")], [(1, "+"), (0, "-")]],
       [1.0, 1.0],
       num_modes=4,
   )
   # One fermionic rotation generated by the number operator n_0 = c_0^† c_0,
   # with the Hartree-Fock reference |0, 1> (modes 0 and 1 occupied).
   generator = FermiOperator([[(0, "+"), (0, "-")]], [1.0], num_modes=4)
   circuit = FermiCircuit(initial_state=[0, 1], gates=[FermiEvGate(generator, 0.3)])

   # A FermiCircuit carries into a Circuit: to_circuit() maps the generators through
   # Jordan-Wigner into the MajoranaGate objects the propagator consumes, and bundles them
   # with the parameter values, mapping, and initial state.
   mp_circuit = circuit.to_circuit()

   mp = MajoranaPropagator(observable, mp_circuit.initial_state, cutoff=4)
   mp.propagate(mp_circuit)
   print(sorted(mp.evolved_operator().items()))  # keyed by Majorana indices

.. testoutput::
   :hide:

   [((0, 2), (-0-0.147760103331j)), ((0, 3), 0.477668244563j), ((1, 2), (-0-0.477668244563j)), ((1, 3), (-0-0.147760103331j))]

Qubit (Pauli) operators
~~~~~~~~~~~~~~~~~~~~~~~~~

The natural starting point when you already hold a qubit Hamiltonian. An
operator is given as a real-coefficient sum of Pauli strings (tensor products of
:math:`I, X, Y, Z`), which are likewise carried into the Majorana basis.

.. testcode::

   from monoprop import PauliPropagator
   from monoprop.pauli_data import PauliOperator, PauliEvGate, PauliEvCircuit

   # Observable: Z⊗Z + 0.5 X⊗X on two qubits.
   observable = PauliOperator(["ZZ", "XX"], [1.0, 0.5])
   # One Pauli rotation exp(-i θ/2 · X_0) acting on qubit 0.
   gate = PauliEvGate([0], PauliOperator(["X"], [1.0]), 0.3)
   circuit = PauliEvCircuit(gates=[gate], initial_state=[], num_qubits=2)
   mp_circuit = circuit.to_circuit()

   # PauliPropagator is the qubit-native simulator: it takes Pauli operators and gates
   # directly, and its cutoff always counts Pauli weight — the qubits a term touches —
   # rather than Majorana modes (see the Notation and Cutoff pages).
   mp = PauliPropagator(observable, mp_circuit.initial_state, cutoff=4)
   mp.propagate(mp_circuit)
   print(sorted(mp.evolved_operator().items())) # WARNING: the keys are Majorana indices - not Pauli strings

.. testoutput::
   :hide:

   [((0, 1, 2, 3), (-0.82533561491+0j)), ((1, 2), (-0-0.5j)), ((1, 2, 3), 0.564642473395j)]


Majorana operators
~~~~~~~~~~~~~~~~~~~

The most direct form: the monomials are specified explicitly as sets of Majorana
mode indices.
The coefficient is the one multiplying the *bare* Majorana product, so it
must keep the monomial Hermitian: real for length-4 monomials, imaginary for
length-2 (since :math:`M_\nu = i^{\binom{|\nu|}{2}} m_{i_1}\cdots m_{i_n}`, see
:doc:`/concepts/notation`).

.. testcode::

   from monoprop import MajoranaPropagator, MajoranaGate, Term, Circuit
   from monoprop.fermi_data import MajoranaOperator

   # Observable given directly as the Hermitian Majorana monomial on indices
   # (0, 1, 2, 3) - a length-4 monomial, so a real coefficient.
   observable = MajoranaOperator([(0, 1, 2, 3)], [1.0], 4)
   # One rotation generated by i·m_3 m_4. Authored directly as a MajoranaGate: a pure
   # generator whose i prefactor folds into the Term's real gen_coeff. A Circuit bundles
   # the gate with the angle value driving it (which angle drives each gate is set by the
   # Circuit's parameter_mapping; the default gives each gate its own).
   gate = MajoranaGate((Term((3, 4), -1.0),))
   circuit = Circuit(gates=[gate], parameters=[0.3])

   mp = MajoranaPropagator(observable, initial_state=[0, 1], cutoff=4)
   mp.propagate(circuit)
   print(sorted(mp.evolved_operator().items())) # WARNING: the keys are Majorana indices - not fermionic

.. testoutput::
   :hide:

   [((0, 1, 2, 3), (0.82533561491-0j)), ((0, 1, 2, 4), (-0.564642473395+0j))]

The reference state
-------------------

Alongside the operator, a simulation needs a **reference state**, typically a
Slater determinant given as the list of occupied orbitals, or computational basis state.
Expectation values are computed against this state or in Schrödinger picture, the state is evolved from this reference.

The circuit
--------------------

Finally, a circuit can be specified as a sequence of *gates*,
each of which is a Majorana rotation. A gate (:class:`~monoprop.MajoranaGate`) is a pure
generator, described by its **terms** - the Majorana monomials :math:`M_\gamma` generating
the rotation :math:`e^{-i\theta M_\gamma/2}`, each a :class:`~monoprop.Term` pairing the
monomial with a real generator coefficient.

A :class:`~monoprop.Circuit` bundles those gates with everything needed to evolve them:
the angle *values* that drive them (:attr:`~monoprop.Circuit.parameters`), the
``parameter_mapping`` wiring each gate to an angle (default: one distinct angle per gate;
``parameter_mapping[i]`` is the angle index driving gate ``i``, and sharing one index across
gates ties their angles together — weight tying), and the reference
:attr:`~monoprop.Circuit.initial_state`. The domain formats produce a ``Circuit`` through
their ``to_circuit()`` method, and two circuits compose temporally with ``+`` (the right
operand's angles are appended on a fresh axis).

A ``Circuit`` is then handed to the propagator via
:meth:`~monoprop.MajoranaPropagator.propagate` (immediate) or
:meth:`~monoprop.MajoranaPropagator.build_graph` (stored for reuse), and the
graph itself owns this gate information — so evaluation takes only the parameter
values (a plain sequence of floats, or the circuit itself). This structure enables the use
of monoprop in variational workflows.
This is the natural representation for algorithms such as ADAPT-VQE, QAOA, etc.
where the circuit grows one generator at a time and is re-evaluated
repeatedly as parameters are optimised.

From input to result
---------------------

The typical flow from a problem definition to a result is:

1. **Express** the operator in fermionic, qubit, or Majorana form, and choose a
   reference state.
2. **Construct** a simulator from the operator, the reference state, and truncation
   settings (such as cutoff type and value).
3. **Propagate** the circuit to build the reusable propagated operator.
4. **Evaluate** expectation values or gradients, re-using that operator across
   many parameter values.

Steps 1-2 happen once; steps 3-4 form the inner loop of a variational
optimisation. The mechanics of steps 3-4 are covered in
:doc:`/concepts/algorithm`, and the concrete API in :doc:`/python-api`.
