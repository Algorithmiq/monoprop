Interface
=========

This page describes, at a conceptual level, how a problem is expressed as input
to monoprop. The authoring interface is **four layers**, each built from the one
below it:

1. **Terms** -- the atoms. A :class:`~monoprop.Majorana` monomial
   (:math:`\gamma_{i_1}\cdots\gamma_{i_w}`) or a :class:`~monoprop.Pauli`
   (letters on named qubits).
2. **Operators** -- a weighted sum of terms, written as a ``{term: coefficient}``
   dict. A :class:`~monoprop.MajoranaOperator`, a :class:`~monoprop.PauliOperator`,
   or a :class:`~monoprop.fermi_data.FermiOperator`. *An operator contains terms.*
3. **Exponential gates** -- an operator (or bare term) that is *exponentiated* to
   drive one variational angle: :class:`~monoprop.MajoranaExp`,
   :class:`~monoprop.PauliExp`, :class:`~monoprop.fermi_data.FermiExp`.
4. **Circuit** -- an ordered sequence of gates, plus angle values and a reference
   state. A single :class:`~monoprop.Circuit` type serves every family: the gates carry the
   family, so a circuit is qubit *or* Majorana/fermionic and rejects a mix of the two.

A circuit is then handed to a **propagator**, which checks its
:attr:`~monoprop.Circuit.family`. For the exact constructors and arguments, see
:doc:`/python-api`.

Whatever term/operator form you choose, it is converted into the Majorana
representation (see :doc:`/concepts/notation`) before simulation.

Where the width lives
---------------------

The total system size -- ``num_modes`` for a Majorana/fermionic problem,
``num_qubits`` for a qubit problem -- lives on the **operator**, and only the
*observable* needs to carry it. Terms are local (a :class:`~monoprop.Pauli` names
only the qubits it touches); gate generators leave the width unset and inherit it
from the propagator (which reads it from the observable). This is why a qubit
:class:`~monoprop.Circuit` takes no ``num_qubits`` argument.

Operator formats
----------------

Fermionic operators
~~~~~~~~~~~~~~~~~~~~~

The natural starting point for quantum chemistry and lattice models. An operator
is given as a weighted sum of products of fermionic creation and annihilation
operators on numbered modes (for example :math:`c_0^\dagger c_1`). monoprop maps
these into the Majorana basis through the Jordan-Wigner transformation.


.. testcode::

   from monoprop import Circuit, MajoranaPropagator
   from monoprop.fermi_data import FermiOperator, FermiExp

   # Observable: the hopping term c_0^† c_1 + c_1^† c_0 on 4 modes
   # ('+' = creation, '-' = annihilation).
   observable = FermiOperator(
       [[(0, "+"), (1, "-")], [(1, "+"), (0, "-")]],
       [1.0, 1.0],
       num_modes=4,
   )
   # One fermionic rotation generated by the number operator n_0 = c_0^† c_0,
   # with the Hartree-Fock reference |0, 1> (modes 0 and 1 occupied). FermiExp is the
   # exponential of that generator; the angle driving it lives in the circuit's parameters.
   generator = FermiOperator([[(0, "+"), (0, "-")]], [1.0], num_modes=4)
   circuit = Circuit(gates=[FermiExp(generator)], parameters=[0.3], initial_state=[0, 1])

   # A Circuit *is* a Circuit -- it converts its fermionic generators into structural
   # MajoranaExp gates at construction, so it feeds the propagator directly. from_circuit
   # reads the circuit's initial state and builds its evolution graph in one step.
   mp = MajoranaPropagator.from_circuit(circuit, observable, cutoff=4)
   print(sorted(mp.evolved_operator(circuit).items()))  # keyed by Majorana indices

.. testoutput::
   :hide:

   [((0, 2), (-0-0.147760103331j)), ((0, 3), 0.477668244563j), ((1, 2), (-0-0.477668244563j)), ((1, 3), (-0-0.147760103331j))]

Qubit (Pauli) operators
~~~~~~~~~~~~~~~~~~~~~~~~~

The natural starting point when you already hold a qubit Hamiltonian. An
operator is a ``{Pauli: coefficient}`` dict; a raw full-width string key like
``"ZZ"`` is shorthand for :class:`~monoprop.Pauli` letters on qubits
``0..len-1``. A :class:`~monoprop.Pauli` term names only the qubits it acts on,
so a gate generator is compact and width-free.

.. testcode::

   from monoprop import PauliPropagator, PauliExp, Circuit, PauliOperator, Pauli

   # Observable: Z⊗Z + 0.5 X⊗X on two qubits. num_qubits lives on the observable only.
   observable = PauliOperator({"ZZ": 1.0, "XX": 0.5}, num_qubits=2)
   # One Pauli rotation exp(-i θ/2 · X_0) acting on qubit 0. PauliExp is the exponential of
   # the Pauli generator; its angle lives in the circuit's parameters. The Circuit takes
   # no num_qubits -- the propagator supplies it from the observable.
   circuit = Circuit(gates=[PauliExp(Pauli("X", 0))], parameters=[0.3], initial_state=[])

   # PauliPropagator is the qubit-native simulator: it takes a Circuit directly, and
   # its cutoff always counts Pauli weight — the qubits a term touches — rather than
   # Majorana modes (see the Notation and Cutoff pages).
   mp = PauliPropagator(observable, circuit.initial_state, cutoff=4)
   mp.propagate(circuit)
   print(sorted(mp.evolved_operator().items())) # WARNING: the keys are Majorana indices - not Pauli strings

.. testoutput::
   :hide:

   [((0, 1, 2, 3), (-0.82533561491+0j)), ((1, 2), (-0-0.5j)), ((1, 2, 3), 0.564642473395j)]


Majorana operators
~~~~~~~~~~~~~~~~~~~

The most direct form: the monomials are specified explicitly as sets of Majorana
mode indices, as ``{Majorana(...): coefficient}`` (a raw index tuple works as a
key too). The coefficient is the one multiplying the *bare* Majorana product, so
it must keep the monomial Hermitian: real for length-4 monomials, imaginary for
length-2 (since :math:`M_\nu = i^{\binom{|\nu|}{2}} m_{i_1}\cdots m_{i_n}`, see
:doc:`/concepts/notation`).

.. testcode::

   from monoprop import (
       MajoranaPropagator, MajoranaExp, Circuit, MajoranaOperator, Majorana
   )

   # Observable given directly as the Hermitian Majorana monomial on indices
   # (0, 1, 2, 3) - a length-4 monomial, so a real coefficient.
   observable = MajoranaOperator({Majorana(0, 1, 2, 3): 1.0}, 4)
   # One rotation generated by i·m_3 m_4. MajoranaExp is the exponential of the
   # MajoranaOperator generator; its coefficients are the *structural* generator
   # coefficients used directly. A Circuit bundles the gate with the angle value
   # driving it (each gate gets its own angle by default; see "Parameters" below).
   circuit = Circuit(gates=[MajoranaExp(MajoranaOperator({(3, 4): -1.0}))], parameters=[0.3])

   mp = MajoranaPropagator(observable, initial_state=[0, 1], cutoff=4)
   mp.propagate(circuit)
   print(sorted(mp.evolved_operator().items())) # WARNING: the keys are Majorana indices - not fermionic

.. testoutput::
   :hide:

   [((0, 1, 2, 3), (0.82533561491-0j)), ((0, 1, 2, 4), (-0.564642473395+0j))]

Exponential gates
-----------------

A gate is the **exponential of a generator**: the operator :math:`G` that, as
:math:`e^{-i\theta G/2}`, drives one variational angle :math:`\theta`. The three
gate types make the exponentiation explicit and differ only in how their
generator is normalized into the Majorana rotation the engine applies:

- :class:`~monoprop.MajoranaExp` -- the generator's coefficients *are* the real
  structural coefficients ``g`` (the layer angle is ``parameters[param] * g``); a
  non-negligible imaginary part is rejected as non-Hermitian.
- :class:`~monoprop.PauliExp` -- each :class:`~monoprop.Pauli` term is
  Jordan-Wigner mapped and antihermitian-normalized when the circuit is ingested.
- :class:`~monoprop.fermi_data.FermiExp` -- a fermionic generator (raw Majorana
  coefficients allowed) is antihermitian-normalized into a structural
  :class:`~monoprop.MajoranaExp` at :class:`~monoprop.Circuit`
  construction.

Each gate accepts either a bare term (a single-term generator with coefficient 1)
or a full operator (a sum). Because the *wrapper type* carries the normalization
rule, the same :class:`~monoprop.MajoranaOperator` means "structural" inside a
:class:`~monoprop.MajoranaExp` and "normalize me" inside a
:class:`~monoprop.fermi_data.FermiExp`; there is no ambiguity.

Parameters
----------

Each gate is the **unit of parameterization**: one gate is driven by exactly one
angle, no matter how many terms its generator has. A multi-term generator is a
single exponential :math:`e^{-i\theta\sum_k g_k M_k / 2}` -- the :math:`g_k` are
fixed structural weights and :math:`\theta` is the single variable. To give
monomials independent angles, author them as separate gates.

The angle index lives on the gate, as its ``param``:

- If **no** gate sets ``param``, each gate gets its own angle in order (the
  identity mapping).
- If **any** gate sets ``param``, **all** must, the indices must be contiguous
  ``0..n-1``, and gates sharing an index share an angle -- this is *weight tying*.

.. testcode::

   from monoprop import MajoranaExp, Circuit, MajoranaOperator, Majorana

   shared = MajoranaOperator({Majorana(0, 1): 1.0, Majorana(2, 3): 0.5})  # multi-term ⇒ ONE angle
   circuit = Circuit(
       gates=[
           MajoranaExp(shared, param=0),          # ┐ gates 0 and 2 share angle 0
           MajoranaExp(Majorana(4, 5), param=1),  # │
           MajoranaExp(shared, param=0),          # ┘
       ],
       parameters=[0.3, 0.7],
   )
   print(circuit.n_parameters, circuit.resolved_mapping)

.. testoutput::

   2 (0, 1, 0)

The reference state
-------------------

Alongside the operator, a simulation needs a **reference state**, typically a
Slater determinant given as the list of occupied orbitals, or computational basis state.
Expectation values are computed against this state or in Schrödinger picture, the state is evolved from this reference.

The circuit
--------------------

A circuit bundles its gates with everything needed to evolve them: the angle
*values* that drive them (:attr:`~monoprop.Circuit.parameters`) and the reference
:attr:`~monoprop.Circuit.initial_state`. The per-gate ``param`` indices give the
parameter mapping (see "Parameters" above). There is a single
:class:`~monoprop.Circuit` type: the gate objects carry the family, so one circuit is
qubit (``PauliExp`` gates) *or* Majorana/fermionic (``MajoranaExp`` / ``FermiExp`` gates,
the latter converted to a structural ``MajoranaExp`` at construction), and it rejects a mix
of the two. Its :attr:`~monoprop.Circuit.family` is what the propagator dispatches on.
Two circuits of the same family compose temporally with ``+`` (the right operand's
angles are appended on a fresh axis).

A circuit is then handed to the propagator via
:meth:`~monoprop.MajoranaPropagator.propagate` (immediate) or
:meth:`~monoprop.MajoranaPropagator.build_graph` (stored for reuse), and the
graph itself owns this gate information — so evaluation takes only the parameter
values (a plain sequence of floats, or the circuit itself). This structure enables the use
of monoprop in variational workflows.
This is the natural representation for algorithms such as ADAPT-VQE, QAOA, etc.
where the circuit grows one generator at a time and is re-evaluated
repeatedly as parameters are optimised.

From input to result
---------------------

The typical flow from a problem definition to a result is:

1. **Express** the operator in fermionic, qubit, or Majorana form, and choose a
   reference state.
2. **Construct** a simulator from the operator, the reference state, and truncation
   settings (such as cutoff type and value).
3. **Propagate** the circuit to build the reusable propagated operator.
4. **Evaluate** expectation values or gradients, re-using that operator across
   many parameter values.

Steps 1-2 happen once; steps 3-4 form the inner loop of a variational
optimisation. The mechanics of steps 3-4 are covered in
:doc:`/concepts/algorithm`, and the concrete API in :doc:`/python-api`.
